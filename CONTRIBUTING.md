# Контрибьюторское руководство — University Schedule System

Спасибо за интерес к проекту! Ниже — всё, что нужно знать, чтобы сделать первый вклад.

---

## 1. Fork и клонирование

1. Нажмите **Fork** на странице [x18255914022/USS](https://github.com/x18255914022/USS).
2. Клонируйте свой форк:
   ```bash
   git clone https://github.com/<ваш-ник>/USS.git
   cd USS
   ```
3. Добавьте upstream-репозиторий:
   ```bash
   git remote add upstream https://github.com/x18255914022/USS.git
   ```

## 2. Рабочая ветка

Всегда создавайте отдельную ветку для каждого изменения:

```bash
git checkout main
git pull upstream main
git checkout -b feat/my-feature   # или fix/my-bug, docs/my-doc
```

Префиксы:
| Префикс | Назначение |
|---------|-----------|
| `feat/` | Новая функциональность |
| `fix/`  | Исправление бага |
| `docs/` | Только документация |
| `refactor/` | Рефакторинг без изменения поведения |
| `test/` | Добавление или исправление тестов |
| `chore/` | Инструменты, CI, зависимости |

## 3. Установка зависимостей

```bash
pnpm install
cp .env.example .env
pnpm --filter @repo/db prisma:generate
pnpm --filter @repo/db prisma:migrate
pnpm --filter @app/api seed
```

Подробности — в [README.md](./README.md) и [docs/DEPLOYMENT.md](./docs/DEPLOYMENT.md).

## 4. Стандарты кода

### TypeScript

- Строгий режим (`strict: true`) в `tsconfig.base.json`.
- Всегда указывайте типы возвращаемых значений у экспортируемых функций.

### ESLint

Проект использует ESLint с `eslint-config-next` (для `apps/web`). Перед коммитом проверяйте:

```bash
pnpm lint
```

Исправляйте ошибки вручную — автозамена не всегда корректна.

### Prettier

Форматирование через [Prettier](https://prettier.io/) (`.prettierrc` в корне). Не отключайте правило:

```bash
pnpm format        # форматировать всё
pnpm format --check # проверить без изменений
```

**Не смешивайте стилистические и логические правки** в одном коммите.

## 5. Commit-сообщения

Проект следует [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <краткое описание>

[опциональное тело]
[опциональный футер]
```

Типы:
| Тип | Когда |
|-----|-------|
| `feat` | Новый функционал |
| `fix` | Исправление |
| `docs` | Документация |
| `style` | Форматирование (без изменения логики) |
| `refactor` | Рефакторинг |
| `test` | Тесты |
| `chore` | Инфра, зависимости |

Область — модуль: `api`, `web`, `bot`, `worker`, `db`, `shared`.  
Пример: `feat(api): add iCal export endpoint`

## 6. Запуск тестов перед PR

```bash
pnpm --filter @app/api test:unit          # unit-тесты (vitest)
pnpm --filter @app/api test:integration   # интеграционные тесты (vitest)
pnpm --filter @app/worker test            # тесты worker (node:test)
```

Все тесты должны проходить зелёным. Новый код — с тестами.

## 7. Pull Request

1. Запушьте ветку:
   ```bash
   git push origin feat/my-feature
   ```
2. Откройте PR в `main` репозитория USS.
3. Заполните шаблон PR:
   - **Что сделано** — кратко опишите суть изменения.
   - **Как проверить** — шаги для ревьюера (URL, команды, сценарий).
   - **Связанные issues** — `Closes #N` или `Refs #N`.
4. Убедитесь, что CI проходит.

### Правила PR

- Одно PR = одно изменение (не миксуйте фичи с рефакторингом).
- Не добавляйте сгенерированные файлы (`.next/`, `node_modules/`, `*.db`).
- Обновляйте документацию, если меняете API или поведение.

## 8. Code Review

- Ревьюеры могут попросить исправления — это нормально, не воспринимайте как критику.
- Отвечайте на каждый комментарий: исправлением или аргументом.
- Squash-коммиты мейнтейнер сливает вручную, force-push не нужен.

## 9. Code of Conduct

Участники проекта обязаны:

- Быть уважительными к другим участникам.
- Принимать конструктивную критику.
- Фокусироваться на том, что лучше для сообщества.
- Не допускать дискриминацию, домогательства, агрессию.

Нарушения — через issue или напрямую мейнтейнеру.
